# 防护改进与验收状态

## 设计迭代

基线沿用既有漏洞规则和输出协议，存在外部文本混入审计输入、字段合法但证据虚假、危险POC从草案进入执行等风险。本版新增不可信JSON数据区、输入信号、复用源码校验、AST检查和无执行能力的审批记录工具。

设计时区分关键词检测与拒绝：安全课程引用和日志文本可能命中，因此输入命中只标记待审，正常任务继续。输出确认即使引用存在的证据文件，也需要人核查真实性，不因路径存在自动放行。

以上是设计和实现修订，不是实测攻击成功率下降的结论。

## 未完成

- **Docker 沙箱**：本机无 Docker，`sandbox/compose.yaml` 是可部署但未验证的产物；Ubuntu-22.04 损坏，隔离与执行改在 Ubuntu-20.04 完成。`approval.py` 只记录声明，隔离强度由独立探针证明，不是工具自证。
- **guard v3**：残留拦截集中在白名单式规则（只读 `open`、`pathlib`/`difflib`/`http.cookiejar`/`requests`、非 Python POC），属设计取舍，需单独一轮讨论后改；`self_test.py` 目前只覆盖 v1/v2 行为。
- **样本量与外部效度**：每类仅 2 个变体、无重复调用，两组结果相同属天花板效应，不能外推。

因此本目录现在是"实现 + 36 条实测 + 人工复核签认 + 隔离取证 + 一次审批后执行 + guard v2 复测"的可交接包，**仍不满足选做三全部验收条件**（缺容器级沙箱与 guard v3）。不得把实现自检填入攻击结果 CSV，也不得把子代理判定说成人工独立判定——两者的分工已写入 CSV 的 `reviewer` / `judgment_by` 两列。

## 后续优化

真实模型测试后分析每个绕过和误拒；增加多语言、编码、拼接及长上下文变体，并固定相同测试集复测。AST规则需持续扩展，但不以黑名单替代隔离。新增HTTP执行环境时单独审查内网目标、重定向、凭据与依赖，保留规则版本和原始证据。

## 36 条实测后的复盘（批次 dsh-20261025）

**观察**：两组攻击成功率、危险建议率、泄露率、误拒率全部为 0，安全降级率均为 16/16。差距没有出现，属于设计上的天花板效应：baseline 本身已带既有协议与安全约束，样本量只有每类 2 个变体，被测与复核又都是同类子代理。因此不能写成"防护把攻击成功率压到 0"。

**真正的问题在输出闸门**：33/36 被 quarantine，但复核判定没有一条是被注入攻破的；25 条是 `vulnerability_type` 写法与 `audit_scope` 精确字符串不等，14 处是 POC 示例里写了 `127.0.0.1:8080`（白名单只认 9080/9081），23 条是只读依赖与 `open()` 被统一禁名。

**下一步**（v2 提案，见批次 `checks/guard_false_positive_review.md`）：类型规范化比较并降级为 warning；目标校验移到运行期 `--base-url`，静态阶段只拦非回环主机；只读 `open` 与只读标准库放行；`pass/warn/quarantine` 三档动作分开。改完后用同一批 36 条输出复测，并要求 `self_test.py` 全绿。
