# 网络安全大实验

本项目记录 LLM 辅助漏洞挖掘的设计、输入样本、提示词、漏洞推理、POC 验证和结果复盘。

流程为：代码预处理 → 提示词设计 → 漏洞分析 → 本地 POC 验证 → 结果校验与优化。

实验不要求训练模型、开发完整审计引擎或复杂扫描框架。各模块以可追溯的代码、判定依据和运行证据交接，静态分析与实测结论分别记录。

**总报告**：[从工作包1到工作包4的实验全过程与主要原理](docs/final_report.md)，内含结果汇总、代表案例、限制、10 页展示提纲与答辩口径。

## 结论与统计口径

- `prediction` 记录“存在候选、未检出候选或无法判定”；`verdict` 记录“确认、待验证或排除”。
- high、medium、low 表示静态证据完整程度，不是漏洞概率，也不是严重程度。没有对应运行证据的候选不能标记为确认。
- P1、P2 表示人工核验顺序，不是 CVSS 评分或最终严重程度。反例列为 P2，不表示已证明安全。
- 结论限于已检查的路径、角色、配置和环境，不推广为整个应用安全。
- 缺少关联输入包时标记 partial，不形成完整父样本判断，也不进入父样本指标。
- 片段、重复依赖、接口和配置条件不自动增加独立样本数。SQL 教学反例不纳入原有样本集的正式指标。
- POC 生成、语法检查、HTTP 200、接口返回 ok 或一次执行失败，都不能单独确定漏洞真伪。未取得真实标签前，不计算误报漏报率或声称 Prompt 性能提升。

## 工作包 4 接手顺序

1. 阅读[工作包 1 交接说明](workpackage1/handoff.md)，确认固定源码版本、样本关系、行号和环境依赖。
2. 阅读[工作包 2 交接说明](prompts/handoff.md)、[输出协议](prompts/output_schema.md)和[POC 约束](prompts/poc_constraints.md)。现有 `prompts/trial/pocs/` 为未运行、需人工适配的草案；其他样本仍需按实验安排生成和保存输出。
3. 阅读工作包 3 主报告、判定矩阵及对应案例，明确成立前提、反例条件和验证成功现象。代表案例不替代全量实验安排。
4. 在授权本地靶场中部署对应源码版本。审计切片不能直接当作独立 Web 页面运行。
5. 在 `verification/` 保存环境、原始脚本、适配差异、命令、响应或浏览器证据；记录样本、路径、角色、配置及实际版本。修改测试仅使用专用对象，记录原值并恢复。
6. 在 `results/` 对照模型结论与实测，区分漏洞判断错误、环境错误、认证问题、脚本错误及证据不足；向工作包 1 至 3 反馈具体问题。
7. 工作包 3 据反馈修订核验条件和案例，工作包 2 据反馈修订 Prompt，按固定条件复测，保留原始输出与证据。

## 串行协作

全组使用原仓库 `main` 分支。同一时间只有一人修改；交接人提交并推送后通知下一位；接手人在无未提交改动时运行 `git pull --ff-only origin main`。

若成员在个人 Fork 或分支准备材料，由负责人确认合并范围并整合至原仓库 `main` 后再交接。个人分支有提交不代表原仓库已更新；基于尚未合并的工作包 2 分支开发时，PR 可能同时包含工作包 2 的提交，需要检查文件差异。

提交前运行 `git status` 和 `git diff --cached` 检查文件。不要提交真实密码、登录 Cookie、令牌、数据库文件和本地虚拟环境。

新增样本使用唯一 ID；本实验中 ID 只表示审计范围，不表示结论。固定模型版本、输入版本、样本集和实际条件后，再比较不同 Prompt。原始模型输出、人工整理稿、复核意见和运行证据分别保存，不覆盖原始记录。
